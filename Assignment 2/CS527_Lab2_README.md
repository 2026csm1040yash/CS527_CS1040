# CS527 Lab 2 – Mini-Computer Simulator

## 1. Project Overview

This project implements the **CS527 Lab 2 mini-computer simulator** in the C programming language.

The simulator models a small computer system with:

1. A compiler for a simple user-level programming language.
2. An instruction memory containing generated bytecode.
3. A data memory containing input/output data.
4. A processor with 256 registers.
5. A program counter (PC).
6. Arithmetic and condition flags.
7. A fetch–decode–execute processor cycle.
8. Labels and conditional/unconditional branches.
9. Final data-memory output written back to a `.byte` file.

The required Lab 2 flow is:

```text
User Program (.txt)
        |
        v
     Compiler
        |
        v
 Program Bytecode
        |
        v
 Instruction Memory
        |
        v
     Processor
        |
        v
   Data Memory
        |
        v
 Final Data File (.byte)
```

The assignment states that compilation and the computer system should be invoked through a single main file and executed as a single executable.

# 3. Compilation and Execution Flow

The simulator follows these stages.

## Stage 1 – Compile the user program

A user-level source file such as:

```text
testcase/spec_example.txt
```

is passed to the compiler.

The compiler reads each line, identifies the instruction, operands, labels, and comments, and generates four-byte instructions.

For example:

```text
x1 = 0
```

becomes:

```text
07 01 00 00
```

The bytecode is stored in a program bytecode file.

---

## Stage 2 – Initialize memory

The memory module loads:

- Program bytecode into instruction memory.
- Data bytecode into data memory.

Instruction memory is:

```text
Instruction[256]
```

Data memory is:

```text
Data[4096]
```

Memory is byte addressable.

Each 32-bit instruction/data value occupies four bytes.

---

## Stage 3 – Reset the processor

The processor reset operation:

- Sets all 256 registers to zero.
- Sets PC to zero.
- Clears processor state as required.

The architecture has:

```text
Register[256]
PC
opcode
dest
src1
src2
Z
N
C
V
```

---

## Stage 4 – Fetch

The processor reads four consecutive bytes starting at the address stored in PC.

The four bytes are interpreted as:

```text
opcode
dest
operand1
operand2
```

The assignment defines the bytecode format as:

```text
<opcode> <dest register> <operand 1> <operand 2>
```

---

## Stage 5 – Decode

The decode stage interprets the instruction fields.

For Lab 2, decode can remain simple because the instruction format already provides the required fields.

---

## Stage 6 – Execute

The processor executes the instruction according to its opcode.

Examples:

```text
ADD
SUB
MUL
DIV
Memory Read
Memory Write
Data Movement
Branch
```

The PC is advanced according to the instruction and branch behavior.

---

## Stage 7 – Finalize

When opcode `0` is encountered:

```text
00 00 00 00
```

the processor terminates simulation.

The final data memory is then written back to the output data file.

---

# 4. Register Architecture

Lab 2 specifies:

```text
Register[256]
```

Therefore the valid register names are:

```text
x0
x1
x2
...
x255
```

Each register is 32 bits.

Examples:

```text
x1 = 10
x2 = 20
x3 = x1 + x2
```

After execution:

```text
x1 = 10
x2 = 20
x3 = 30
```

---

# 5. Constants

Constants are supported from:

```text
0 to 255
```

Examples:

```text
x1 = 10
x2 = x1 + 20
x3 = x2 - 5
```

A constant is encoded differently from a register operand.

This distinction is important because Lab 2 provides separate opcodes for:

- register/register arithmetic
- register/constant arithmetic

# 6. Arithmetic Operations

The language supports:

```text
+
-
*
/
```

## Register + Register

Example:

```text
x3 = x1 + x2
```

Bytecode:

```text
01 03 01 02
```

Meaning:

```text
01 = ADD
03 = destination register x3
01 = source register x1
02 = source register x2
```

---

## Register + Constant

Example:

```text
x3 = x1 + 10
```

The constant form uses the constant-version opcode.

The assignment provides separate opcodes for arithmetic operations with a constant.

---

## Subtraction

Example:

```text
x3 = x1 - x2
```

Uses the subtraction opcode.

---

## Multiplication

Example:

```text
x3 = x1 * x2
```

Uses the multiplication opcode.

---

## Division

Example:

```text
x3 = x1 / x2
```

Uses the division opcode.

Division by zero must not be used in valid test programs.

---

# 7. Condition Flags

Addition and subtraction update four global flags:

```text
Z
N
C
V
```

## Z – Zero Flag

`Z = 1` when the result is zero.

Example:

```text
x3 = x1 - x1
```

Result:

```text
0
```

Therefore:

```text
Z = 1
```

---

## N – Negative Flag

`N = 1` when the most significant bit of the 32-bit result is 1.

For signed 32-bit values this represents a negative result.

---

## C – Carry Flag

For addition:

```text
C = 1
```

when the unsigned result wraps around and is strictly smaller than either unsigned input.

For subtraction:

```text
C = 1
```

when operand 1 is greater than operand 2, according to the Lab 2 specification.

---

## V – Overflow Flag

For addition:

Overflow occurs when:

- Both operands have the same sign.
- The result has a different sign.

For subtraction:

Overflow occurs when:

- The operands have different signs.
- The result's sign matches the original sign of operand 2.

---

# 8. Memory

Memory is byte addressable.

The assignment specifies:

```text
Instruction[256]
Data[4096]
```

Each 32-bit value occupies four bytes.

For example, a 32-bit value is stored as four individual bytes.

The bytecode files use four hexadecimal bytes per line:

```text
AA BB CC DD
```

The assignment gives:

```text
FF FF FF FF
```

as the four-byte representation of `-1` in its specified representation.

---

# 9. Memory Read Operations

Lab 2 introduces square-bracket addressing.

## Variable Address

Example:

```text
x1 = [x2]
```

Meaning:

1. Take the value in `x2` as a memory address.
2. Read the 32-bit value from that address.
3. Store it in `x1`.

The bytecode format for memory read uses:

```text
opcode destination 0 address_register
```

For example:

```text
5 4 0 3
```

means:

```text
Memory Read
destination = x4
operand1 = 0
address/source register = x3
```

The important Lab 2 correction is that **operand 1 must be zero** for memory read/write and data-movement instructions.

---

## Constant Address

Example:

```text
x1 = [0]
```

The address is a constant.

The assignment specifies a separate memory-read-constant opcode.

For this Lab 2 version:

```text
0x0D
```

is used for memory read with a constant address.

---

# 10. Memory Write Operations

## Variable Address

Example:

```text
[x2] = x1
```

Meaning:

1. Read the address from `x2`.
2. Read the value from `x1`.
3. Store the value into memory at that address.

The bytecode has the form:

```text
06 destination_address_register 0 source_value_register
```

For example:

```text
6 3 0 2
```

means:

```text
Memory Write
address register = x3
operand1 = 0
value register = x2
```

---

## Constant Address

Example:

```text
[10] = x1
```

This writes the value in `x1` to constant address `10`.

The constant-address memory-write opcode is used for this form.

---

# 11. Legacy READ and WRITE

Lab 2 says that:

```text
Read
Write
```

are legacy instructions.

They should not normally be used in new Lab 2 programs, but the compiler must still be able to compile them.

Example:

```text
Read x1 0
Write x1 4
```

The compiler therefore retains support for these instructions.

For memory instructions, the updated bytecode convention uses:

```text
operand1 = 0
```

where required.

---

# 12. Data Movement

Lab 2 supports:

```text
x1 = 10
```

This is a data-movement instruction.

The destination register receives the constant.

Example:

```text
x1 = 0
x2 = 10
x3 = 255
```

The corresponding instruction uses the data-movement opcode.

The assignment defines:

```text
Variable: x0 to x255
Constant: 0 to 255
```

---

# 13. Comments

Comments begin with:

```text
%
```

Everything after `%` on that line is ignored.

Example:

```text
x1 = 0 % initialize index
```

The compiler processes:

```text
x1 = 0
```

and ignores:

```text
% initialize index
```

Comments are useful for explaining test programs without affecting generated bytecode.

---

# 14. Labels

Labels are used as branch destinations.

A label:

- Must begin with `.`
- Must be the first character on the line.
- May contain alphanumeric characters.
- Must not contain special symbols.
- Must not contain `:`.
- Must not have another expression on the same line.

Correct:

```text
.loop
```

Incorrect:

```text
    .loop
```

Incorrect:

```text
.loop:
```

---

# 15. Branch Instructions

Branch instructions have the general form:

```text
B<suffix> <label>
```

Examples:

```text
BEQ .loop
BGE .exit
BAL .loop
```

Branches use condition flags.

The assignment defines branch instructions using:

```text
0x10 + branch condition code
```

The branch bytecode format is:

```text
<opcode> 0 0 <relative offset>
```

Therefore the second and third bytes are zero.

---

# 16. BAL and `1E 00 00 FA`

One particularly important instruction is:

```text
BAL .loopback
```

`BAL` means:

```text
Branch Always
```

The generated opcode is:

```text
1E
```

So an instruction such as:

```text
1E 00 00 FA
```

means:

```text
opcode = 1E
dest = 0
operand1 = 0
relative offset = FA
```

`FA` is the 8-bit representation used for a negative relative offset.

Therefore this instruction can jump backwards to the loop label.

The official Lab 2 example itself contains:

```text
1E 0 0 FA
```

for the loop-back branch.

---

# 17. Relative Branch Offset

Branch targets are not stored as absolute instruction addresses.

Instead, the bytecode stores a relative offset.

The assignment specifies:

```text
next instruction address =
current instruction address + offset
```

The offset may be positive or negative.

For a backward loop, the offset is represented using an 8-bit two's-complement value.

For example:

```text
FA
```

represents:

```text
-6
```

when interpreted as a signed 8-bit value.

---

# 18. Important Bytecode Correction

For the updated Lab 2 specification, the following convention is important:

### Memory read/write and data movement

The first operand field is zero.

Therefore:

```text
x4 = [x3]
```

is represented as:

```text
05 04 00 03
```

and:

```text
[x3] = x2
```

is represented as:

```text
06 03 00 02
```

Do not incorrectly generate:

```text
05 04 03 00
```

or:

```text
06 03 02 00
```

for these forms.

# 19. Opcode Table

The Lab 2 opcode organization is:

| Operation | Register/Variable Opcode | Constant Opcode |
|---|---:|---:|
| Add | `0x01` | `0x09` |
| Subtract | `0x02` | `0x0A` |
| Multiply | `0x03` | `0x0B` |
| Divide | `0x04` | `0x0C` |
| Memory Read | `0x05` | `0x0D` |
| Memory Write | `0x06` | `0x0E` |
| Data Movement | `0x07` | `0x0F` |
| Branch | `0x10 + condition code` | — |

**Important:** memory-read constant is `0x0D`.

This is one of the Lab 2 discrepancies that must be handled correctly.

# 20. Four-Byte Instruction Format

Every instruction occupies exactly four bytes:

```text
Byte 0     Byte 1     Byte 2     Byte 3
 opcode     dest       src1       src2
```

Example:

```text
01 02 02 06
```

can be interpreted as:

```text
01 = ADD
02 = destination x2
02 = source x2
06 = source x6
```

Therefore:

```text
x2 = x2 + x6
```

---

# 21. Termination Instruction

The processor terminates when opcode `0` is encountered.

The normal termination instruction is:

```text
00 00 00 00
```

The processor sets:

```text
end_of_simulation = 1
```

when opcode zero is encountered.

---

# 22. Processor Functions

The processor contains four main functions:

```text
reset()
fetch()
decode()
execute()
```

## reset()

Initializes:

```text
Register[256]
PC
```

and processor state.

---

## fetch()

Reads four bytes starting at the current PC:

```text
Instruction[PC]
Instruction[PC + 1]
Instruction[PC + 2]
Instruction[PC + 3]
```

These become:

```text
opcode
dest
src1
src2
```

---

## decode()

The Lab 2 specification describes decode as a `void` function and empty at this stage.

The instruction fields can therefore be interpreted directly during execution.

---

## execute()

Performs the operation represented by the opcode.

Examples:

```text
ADD
SUB
MUL
DIV
READ
WRITE
MOV
BRANCH
```

---

# 23. Main Program

The main program connects all modules.

Conceptually:

```text
main()
{
    compile();
    initialize();
    reset();

    while (!end_of_simulation)
    {
        fetch();
        decode();
        execute();
    }

    finalize();
}
```

The assignment describes the required compilation, initialization, reset, processor loop, and finalization sequence.

The user-level program should be supplied through command-line arguments.

# 28. Official Example Program

The Lab 2 document gives an array-sum example.

A simplified version is:

```text
x1 = 0
x2 = 0
x3 = 0
x4 = [x3]

.loopback
x15 = x1 - x4
BEQ .exit
x3 = x3 + 4
x6 = [x3]
x2 = x2 + x6
x1 = x1 + 1
BAL .loopback

.exit
[x3] = x2
```

The purpose is to:

1. Initialize an index.
2. Initialize the sum.
3. Initialize the array address.
4. Read the array size.
5. Compare the current index with the size.
6. Exit when they are equal.
7. Move to the next array element.
8. Read the element.
9. Add it to the sum.
10. Increment the index.
11. Branch back to the loop.
12. Store the final result.

The official specification gives this example and its corresponding bytecode.

# 33. Test Case 5 – Runtime Sum

The runtime sum test demonstrates why branches and labels are required.

The data layout is:

```text
Address 0x00       -> N
Address 0x04       -> element 1
Address 0x08       -> element 2
Address 0x0C       -> element 3
...
```

The assignment specifies this layout for the runtime array example.

The program:

1. Reads N from address `0`.
2. Initializes index and sum.
3. Loops through the array.
4. Uses `BEQ` to exit.
5. Uses `BAL` to return to the loop.
6. Writes the final sum.

This test is the reason you see:

```text
1E 00 00 FA
```

in the generated bytecode.

`1E` is `BAL`, and `FA` is the negative relative offset used to jump back to the loop.

# 35. Output Files

There are two different types of output that should not be confused.

## Compiler terminal output

This shows generated instructions:

```text
07 01 00 00
07 02 00 00
...
```

This is useful for checking whether the compiler generated the correct bytecode.

## Data `.byte` output

This contains the final contents of data memory after processor execution.

This is useful for checking whether the processor executed the generated program correctly.

Do not put explanatory text inside a `.byte` file if that file will be read by the simulator.

For example, this is valid:

```text
16 00 00 00
```

but this should not be placed into a machine-readable byte file:

```text
Result = 22
```

Keep explanations in separate `.txt` or README files.

# 36. Debugging Checklist

If the compiler generates no instructions:

1. Check the input filename.
2. Check that the program contains valid instructions.
3. Check that the file is in the correct directory.
4. Check that comments begin with `%`.
5. Check register names such as `x1`, `x2`, etc.

If `gcc: fatal error: no input files` occurs during linking:

1. Check the Makefile.
2. Make sure `SRC = $(wildcard *.c)` finds the C files.
3. Make sure all `.c` files are in the same directory as the Makefile.
4. Run:

```powershell
mingw32-make clean
mingw32-make
```

If the compiler runs but generates wrong bytecode:

1. Check whether the operand is a register or constant.
2. Check the opcode.
3. Check operand positions.
4. Check memory-read/write operand 1.
5. Check branch offset calculation.
6. Check label addresses.

If the loop never terminates:

1. Check the comparison instruction.
2. Check the flags.
3. Check the branch condition.
4. Check the branch offset.
5. Check whether `BAL` points to the correct label.

# 37. Common Bytecode Mistakes

### Mistake 1 – Wrong memory-read operand position

Incorrect:

```text
05 04 03 00
```

Correct:

```text
05 04 00 03
```

for:

```text
x4 = [x3]
```

---

### Mistake 2 – Wrong memory-write operand position

For:

```text
[x3] = x2
```

correct:

```text
06 03 00 02
```

---

### Mistake 3 – Wrong constant memory-read opcode

For constant memory read, use:

```text
0D
```

not:

```text
0C
```

`0C` is the constant version of **divide**.

---

### Mistake 4 – Removing `1E 00 00 FA`

Do not remove:

```text
1E 00 00 FA
```

from a program containing:

```text
BAL .loopback
```

It is the loop-back branch.

---

### Mistake 5 – Putting explanations in `.byte`

Machine-readable bytecode files should contain only byte values.

Use a separate explanation file for comments and expected results.
